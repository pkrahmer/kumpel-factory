## 2. The five-minute prompt cache: make it persistent and documented

On 2026-11-08 the prefix comparison of the 36 measured runs showed that no run reads another run's start beyond Claude Code's own 6,683 tokens: Claude Code puts its cache breakpoint after the role and the run's facts, so the shared work item is never reused across runs. The one-hour cache (written at twice the input price) therefore only costs. As a trial, `CLAUDE_CODE_PROMPT_CACHE_TTL=5m` and `FACTORY_CONTAINER_ENV=CLAUDE_CODE_PROMPT_CACHE_TTL` were added by hand to `factory.local.env` of the instances `vm` and `demo3`.

If the next runs show `ttl: 5m` in their transcripts and the cache writes cost less: make it persistent (the factory sets it for every Claude Code run, or `setup.sh` and the template write it) and document it (the operator guide's agent runtime and settings, `docs/decisions.md`). The cross-session experiment (2026-11-08, 19:04 UTC, six sessions in the demo3 stage image, about $0.19) answered the open test: the five-minute cache works (`ephemeral_5m` writes); the 6,683 tokens every run reads are the tools, Claude Code's part and the factory's system prompt, so the system part is already shared across runs and does not change per run; an identical message is read whole by the next session; a message that differs anywhere, even only at its end, is not read at all, because Claude Code's only message breakpoint sits at its end. The message variants (19:07 UTC, four sessions, about $0.36): (A) the role's instructions in a system prompt per role let a later run of the same role read them (10,297 tokens instead of 6,683 with the coder's role), with no extra turn; (B) the shared part as a message of its own, the run's facts in a second message, lets the next session read the whole shared part, but costs a turn of its own, in which the agent answers the first message before it sees the facts. Both pay only for runs within the cache's time, and B only where the shared part is identical: the work item grows by an entry at every stage, so it is identical only for a retry. The split variant (19:14 UTC, a real story played as three stages in a row): with the story text from its title to the journal in the system prompt, and the role, the journal and the facts in the message, every stage after the first reads the story text from the cache whatever its role (10,097 tokens read instead of 6,633; first request 18-22 % cheaper; about $0.016 a run, $0.5 a feature, about 5 %), when it starts within the cache's time. CLAUDE.md is not in the shared part either: Claude Code puts it as the first block of the first message, with no cache point after it, so every run writes it anew (9,477 characters in the demo, about 21,000 in kumpel-factory); in the system prompt, before the story, it is shared by every run of the project: tested at 19:18 UTC with `CLAUDE_CODE_DISABLE_CLAUDE_MDS=1` (Claude Code then does not load it; `--setting-sources user` works too but drops the project's settings), kumpel-factory's CLAUDE.md (7,284 tokens) was read by the next runs of other roles and other work, and their first request cost 46 % less (about $0.035 a run at the API price list). Also a candidate: the "Rules" section the role files share (6,582 characters, the same in all seven roles), placed first. Not a candidate: files the agents read, since in F0058 and F0059's 120 runs no file was read by more than 24 runs (the 14 runs that read their own work item file mostly ran before F0058-S0002 put it into the message; the later ones need the file: line numbers, intake's edit). The order would run from the most to the least shared: the factory's system prompt, the shared rules, CLAUDE.md, the story text. Totals (19:25 UTC, replayed on the real runs' times): Claude Code's one cache point at the end of the system prompt allows either P (the shared rules and CLAUDE.md, shared by every run of the project) or S (P and the story text, shared within a story; a new story's first run misses all of it). With the five-minute cache: demo3 P 11 %, S 14 %; F0058 and F0059 on vm P 13 %, S 11 % (nearly every gap between runs is under five minutes). The one-hour cache would save 18-23 % but its writes cost 32-34 % more: a net loss, so the five-minute cache stays. P is the simpler choice and wins on kumpel-factory itself: there S misses 25 runs against P's 3 (15 new work items, six of them acceptances, and 10 changes of the story text inside a story: intake's rewrite, answers written into the Interface, criteria added after a review), every miss loses CLAUDE.md too, and the story text averages only about 1,000 tokens against CLAUDE.md's 7,300. To weigh: the story then stands in the system prompt, which today says the work item is data. Open with it: whether reuse of the role and the work item across runs is worth a design (the role's instructions in a system prompt per role, the work item as a message of its own, or the API without Claude Code).
